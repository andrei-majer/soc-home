Why two states? The whole fabric was armed back in Plan 6. vr_quarantine is a new actuator added in Plan 7 and deliberately not yet loaded into the live process — its first action would cut your own .13 workstation off the flat LAN, so going live is a manual, observed step (this guide). Nothing about the base fabric changed.

2 · What vr_quarantine does

On a managed-host isolate decision, the dispatcher now composes two actuators:

  • router_isolate — adds the host to the contain_host nft set on the R7800 (north–south / gateway drop).
  • vr_quarantine — schedules Velociraptor's Windows.Remediation.Quarantine (a Windows local IPsec policy named VelociraptorQuarantine) on the host's pinned VR client. This is the L2 lockdown the gateway drop can't do on a flat /24 — it stops same-subnet lateral movement.
Fail-safe by design. vr_quarantine confirms enforcement (polls flows() to FINISHED) before recording containment. If it can't confirm, the result is pending → a loud L2 UNCONFIRMED Telegram alert and no containment row is written (never a false "contained"). DNS is permitted only to 192.168.1.1; the artifact also auto-keeps the VR-server path and self-removes if it would cut itself off.

3 · Arm it — the observed round-trip

⚠ This makes the SOC able to cut .13 (your workstation) off the LAN. Do the first fire observed, from a session that survives the cutoff (the .20 console or Tailscale, not a LAN SSH from .13), with the break-glass (§7) ready. The release-host command and the kill-switch are your undo.
1

Preview with a dry-run (no action)

The CLI loads current code, so this already exercises the new vr_quarantine routing without touching .13:

soc-contain --dry-run dispatch --rule-id 100307 --src-ip 192.168.1.13 --category canary
# expect: decision=True … actions=['vr_collect', 'vr_quarantine', 'router_isolate']
2

Fire it for real — watch .13

From the .20 console (config is already dry_run: false):

soc-contain dispatch --rule-id 100307 --src-ip 192.168.1.13 --category canary
soc-contain status
# status should show host=192.168.1.13 with BOTH vr_quarantine and router_isolate

On .13 you should lose LAN reachability to everything except DNS→.1, DHCP, and the VR server. Tailscale still reaches it. Confirm the IPsec policy is present:

# on .13, elevated:
netsh ipsec static show policy all   # → VelociraptorQuarantine, assigned
3

Release — confirm it reverses cleanly

soc-contain release-host 192.168.1.13
soc-contain status                   # → no active containments

On .13, LAN connectivity returns and netsh ipsec static show policy all no longer lists an assigned VelociraptorQuarantine. This apply→remove round-trip is the proof the lockdown is reversible.

4

Verify break-glass (server-independent removal)

Confirm you can lift the policy without the soc-contain/VR channel — see §7. Then update the runbook with the exact netsh ipsec static commands you confirmed (methods C/D are marked unverified until you do this).

5

Make the live alert path use the new code

Steps 1–3 used the CLI. The long-running receiver (what real Wazuh alerts hit) still holds old code until restarted:

systemctl restart soc-contain-receiver
systemctl is-active soc-contain-receiver   # → active

Also confirm the Wazuh-AR caller's HTTP timeout exceeds QUARANTINE_CONFIRM_TIMEOUT (30 s) so a confirm-poll doesn't look like a failure to the manager.

6

Live

The next real managed-host canary (or confirmed-C2 trip on .13) now applies the L2 lockdown automatically. Keep the kill-switch within reach (§6).

6 · Emergency stop & disarm

GoalCommand
Instant brake (halt ALL new actions — auto + approve)touch /etc/soc-contain/DISABLED  or  soc-contain disable
Resumerm /etc/soc-contain/DISABLED  or  soc-contain enable
Release one host (all its rows)soc-contain release-host <src_ip>
Release one containment by idsoc-contain release --id <n>
Full disarm (back to log-only)set soc_contain_dry_run: true in soc-ansible host_vars → ansible-playbook playbooks/site.yml --limit suricata-20
The kill-switch stops new containment; it does not undo bans already in place. It persists across reboot (file on disk), so it's safe as a "don't act until I say so" hold.

7 · Break-glass — lift the IPsec lockdown without the server

If the operator is locked out or the VR channel is down. Full detail: docs/runbooks/soc-contain-quarantine-breakglass.md. In order of preference:

#MethodHow
ANormal (VR up)soc-contain release-host 192.168.1.13 on .20
BVR serverRe-run Windows.Remediation.Quarantine on the client with RemovePolicy (GUI, or CLI — confirm the --client_id flag)
CLocal VR binary on .13velociraptor.exe artifacts collect Windows.Remediation.Quarantine --args RemovePolicy=Y (elevated)
DRaw, no VRelevated on .13 — see below
# Method D — raw IPsec removal (NOT Windows Firewall). Confirm exact syntax during arming.
netsh ipsec static show policy all
netsh ipsec static set policy name="VelociraptorQuarantine" assign=no   # lifts the block
netsh ipsec static delete policy name="VelociraptorQuarantine"          # cleanup
# confirm restored:
Test-NetConnection 192.168.1.1 ; Resolve-DnsName example.com
The Method-D netsh ipsec static commands are not yet executed on .13 — confirm and update the runbook during the arming round-trip (§3, step 4).
